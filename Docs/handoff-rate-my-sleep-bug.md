# Handoff Brief — Lull Live Activity: Rate-My-Sleep Tap Not Working

## TL;DR

Tapping a rating dot on the "How did you sleep?" Live Activity card produces a faint visual press feedback but no subsequent state change — no confirm card, no activity dismissal, no reward sheet on next app foreground. Mid-Sleep mode tap now works correctly (different code path: URL scheme + `Link` + `widgetURL`). The rating dots use `Button(intent: LiveActivityIntent)`, which is where the failure lives.

## Feature spec

The Sleep Companion Live Activity runs across the user's overnight sleep window with three phases:

1. **`.sleeping`** — moon icon + countdown to wake + "Mid-Sleep mode" tap target.
2. **`.awaitingRating`** — sun icon + "How did you sleep?" + 5 numbered rating dots (1=Wrecked … 5=Great).
3. **`.rated`** — checkmark + "Your score is saved" + score (e.g. `6.0  +3.0 VS BASELINE`).

The view auto-promotes `.sleeping` → `.awaitingRating` based on the clock (`SleepCompanionViews.swift:13-20` — `var effectivePhase: Phase`), so the wake card surfaces even though the stored phase hasn't been updated.

Intended UX on dot tap:

1. Within ~100ms, card flips to `.rated` showing checkmark + "Your score is saved" + `—` placeholder for score.
2. Card lingers ~60s, auto-dismisses.
3. If user taps the confirm card during the 60s window → app opens to `MorningRewardView` with real numeric score + delta filled in.
4. If user instead opens the app naturally later → `MorningRewardView` still surfaces (the App Group rating write happens regardless of visual state).

## Architecture

- **App target** (`Lull/`): `AppState`, `LiveActivityService`, `LullApp`, dashboards, etc.
- **Widget extension target** (`LullActivities/`): `SleepCompanionWidget`, `SleepCompanionViews`, `LullRateSleepIntent`, `LullOpenMidSleepIntent`, `LullActivitiesBundle`. Bundle ID `com.trylull.app.activities`.
- **Shared source** (compiled into both targets): `Lull/LiveActivity/LullSleepAttributes.swift` (the `ActivityAttributes`).
- **App Group** `group.com.trylull.app` — entitlement on both targets, used to pass rating data from extension to app.
- **URL scheme** `lull://` — registered in `Lull/Resources/Info.plist` via `CFBundleURLTypes` (regenerated by xcodegen from `project.yml`). Handled in `LullApp.swift:35-39` via `.onOpenURL`.
- **iOS deployment target**: 17.0.
- **Swift version**: 5.10.

## What's been tried for the rating bug, in order

1. **Original implementation** — `LullRateSleepIntent` was a `LiveActivityIntent` with `openAppWhenRun = true`, `perform()` wrote rating to App Group + called `activity.update` setting `phase = .awaitingRating, rating = n` (just filled dots, didn't switch to confirm card). Confirm card was supposed to come later from `publishRatedAndEnd` on app foreground. Symptom: dots filled, but confirm card only appeared minutes later when app eventually foregrounded — and sometimes never, because `openAppWhenRun` on `LiveActivityIntent` is unreliable on iOS 17.

2. **Move `.rated` push into the extension** — Changed intent to set `phase = .rated, rating = n, score = nil` (score filled in by app later). Confirm card rendered correctly on tap. But the activity stayed alive indefinitely because `publishRatedAndEnd` only runs on app foreground, and most users never foreground after rating from the Lock Screen.

3. **Schedule auto-dismissal via `activity.end(dismissalPolicy: .after(Date()+60s))`** — first tried `activity.end(content, …)` alone with no preceding update. Card never rendered (apparently ending with content from the extension is flaky about applying the new state). Then tried `activity.update(content)` followed by `activity.end(content, dismissalPolicy: .after(60s))`. Builds clean.

4. **Realized `openAppWhenRun = true` was preempting the awaits** — when the intent's `perform()` returns, iOS launches the host app and suspends the extension before the awaited `activity.update` / `activity.end` calls flush to the system. Set `openAppWhenRun = false`. This was supposed to be the fix.

5. **Added `.widgetURL("lull://reward")` on `ConfirmLockCard`** so tapping the rendered confirm card opens the app to the reward sheet.

After all of the above, user reports the rating dots still produce only a faint visual press feedback and no state change.

## Hypotheses for the remaining bug (ranked)

### 1. The intent isn't actually firing (most likely)

The faint button-color change the user sees is SwiftUI's default press feedback — it does NOT prove `perform()` is being invoked. Possible reasons:

- **`LiveActivityIntent` + `Button(intent:)` flakiness on iOS 17.x.** Multiple Apple Developer Forum reports of `Button(intent:)` silently no-op'ing when the intent is `LiveActivityIntent`. Mid-Sleep button works because it's a `Link`, not a `Button(intent:)`.
- **`@Parameter` serialization edge case.** The intent has `@Parameter(title: "Rating") var rating: Int` and an `init(rating: Int)`. iOS's AppIntents bridging sometimes drops parameters set via the convenience init when crossing the SwiftUI-to-extension boundary. Worth testing without `@Parameter`.
- **Stale extension binary.** Although Mid-Sleep changes took effect after reinstall, a Live Activity that's *already running* may have captured the OLD view code at start time. Each iteration on the extension requires: (a) rebuild, (b) end the current activity, (c) start a fresh one. The user may be tapping on a stale activity that has stale button bindings.

### 2. The intent fires but `Activity<…>.activities` is empty

The extension's `activity.end(…)` removes the activity from `Activity<LullSleepAttributes>.activities`. If the user tapped once before, then taps again expecting the card to update — the loop has nothing to iterate over. First tap fails silently, every subsequent tap also fails silently. Likely a co-symptom, not the root cause, since user reports even single-tap scenarios fail.

### 3. `activity.update` + `activity.end` back-to-back from the extension is racy

The `await activity.update(content)` schedules a system-side update; `await activity.end(content, dismissalPolicy: .after(60s))` immediately after may invalidate or coalesce with it, ending up showing no new state. Apple's ActivityKit docs don't explicitly forbid this but don't recommend it either.

### 4. Dynamic Island bottom region eats the tap

The DI's expanded view has its own implicit "tap-to-open-app" gesture. `Button(intent:)` inside a `DynamicIslandExpandedRegion(.bottom)` may be losing the tap to that ambient gesture. If true, the Lock Screen `WakeLockCard` rating dots should still work and only DI dots fail — the user hasn't explicitly distinguished which surface they tested.

## Suggested next steps for Codex (in priority order)

### Step 1 — Diagnose, don't change code yet

Add `os_log` or `print` statements at three points in `LullRateSleepIntent.perform()`:

```swift
func perform() async throws -> some IntentResult {
    print("[LullRateSleepIntent] perform() called with rating=\(rating)")
    // … App Group write …
    print("[LullRateSleepIntent] activities count = \(Activity<LullSleepAttributes>.activities.count)")
    // … loop …
    print("[LullRateSleepIntent] perform() returning")
    return .result()
}
```

Run on device. Open Console.app on Mac → connect device → filter by process name `LullActivities` (or subsystem `com.apple.ActivityKit`). Tap a rating dot.

- If NO "perform() called" log appears → intent is not firing. Bug is at the `Button(intent:)` layer. Skip to step 2.
- If "perform() called" appears but `activities count = 0` → activity was already ended. Restart with a fresh activity.
- If logs appear but card still doesn't update → bug is in the `activity.update` / `activity.end` calls. Try variations in step 3.

### Step 2 — If the intent isn't firing, swap to a per-rating-value intent without `@Parameter`

Rule out `@Parameter` serialization as the culprit. Create five no-parameter intents and route by type:

```swift
struct LullRate1Intent: LiveActivityIntent { … perform calls shared helper with rating=1 … }
struct LullRate2Intent: LiveActivityIntent { … rating=2 … }
…
```

Use them in `RatingDotRow`:

```swift
let intent: any LiveActivityIntent = {
    switch n {
    case 1: return LullRate1Intent()
    case 2: return LullRate2Intent()
    …
    }
}()
Button(intent: intent) { … }
```

Crude but eliminates parameter-passing as a variable.

### Step 3 — If intent fires but state doesn't update, simplify the update path

Try variant A — update only, no end (re-introduces the lingering-island bug temporarily, but isolates whether `update` alone works):

```swift
for activity in Activity<LullSleepAttributes>.activities {
    var state = activity.content.state
    state.phase = .rated
    state.rating = rating
    await activity.update(ActivityContent(state: state, staleDate: nil))
}
```

If the confirm card renders, variant A confirms `update` works and the bug is in the `end` overlap.

Then try variant B — end only, no preceding update, with full content:

```swift
for activity in Activity<LullSleepAttributes>.activities {
    var state = activity.content.state
    state.phase = .rated
    state.rating = rating
    await activity.end(
        ActivityContent(state: state, staleDate: nil),
        dismissalPolicy: .after(Date().addingTimeInterval(60))
    )
}
```

If variant B renders the confirm card AND auto-dismisses, that's the right shape. If it doesn't render, ending-with-content from the extension is broken on this iOS version.

### Step 4 — If both update and end are flaky, abandon the extension-side flip

Fall back to the "URL scheme everywhere" pattern that works for Mid-Sleep:

- Make the rating dots `Link(destination: URL(string: "lull://rate?score=\(n)")!)` instead of `Button(intent:)`.
- Add a `lull://rate?score=N` handler in `LullApp.onOpenURL` that writes the rating to the App Group and immediately triggers `ingestPendingLiveActivityRating`.
- Cost: app must launch to record the rating (no extension-side instant feedback). The dots no longer fill in the live activity — but the app opens fast, the reward sheet appears immediately, and the activity ends via `publishRatedAndEnd`.

This is a less elegant UX but it's the most reliable path on iOS 17, mirroring what already works for Mid-Sleep.

### Step 5 — DI-specific testing

Have user explicitly test BOTH surfaces and report which fails:

- **Lock Screen** (`WakeLockCard`): full-width card with rating dots.
- **Dynamic Island expanded** (`DIWakeBottom`): smaller dots in the bottom region.

If only DI fails, the fix is DI-specific (likely tap-eaten-by-region issue). If both fail, the issue is in the intent or `RatingDotRow` shared code.

## Useful pointers

- **Live Activity logs in Console.app**: filter subsystem `com.apple.ActivityKit` or process name `LullActivities`. Most useful diagnostic available.
- **App Group inspection**: easier via in-app debug button that prints `UserDefaults(suiteName: "group.com.trylull.app")?.dictionaryRepresentation()` than via shell.
- **Iteration loop**: rebuilding the widget extension does NOT swap views into a running Live Activity. Every code change requires ending the current activity and starting a fresh one. `LiveActivityService.shared.endCurrentSleepActivity()` exists for this — wire it to a debug button if not already.
- **Latest commit**: changes from this session are uncommitted — run `git diff` to see everything touched since `2ff915d`.
- **Testing without overnight wait**: turn off "Set Automatically" in iOS Settings → General → Date & Time, then manually advance the clock past the typical wake time. The `effectivePhase` flip is clock-based, so the wake/rating card will surface within a few seconds.

## Critical gotcha for iteration

When iterating on the widget extension code, **start a fresh Live Activity for each test**. iOS does NOT swap view code into an already-running activity; the views are captured at activity-start time. End any existing one (`LiveActivityService.shared.endCurrentSleepActivity()`) before each test cycle, or changes won't appear to take effect.
